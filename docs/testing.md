# Тесты

Для нативного запуска нужен Go 1.26.1 или новее; для контейнеров нужен Docker.

## Быстрый запуск

```sh
make integration   # Unit, интеграционные и E2E тесты с race detector
make e2e           # Только полный HTTP-сценарий бота
```

Compose поднимает отдельную тестовую PostgreSQL. Проверки используют отдельные схемы и диапазоны ID пользователей; данные demo не очищаются. Тесты не входят в runtime-бинарник.

## GitHub Actions

CI запускается для push в `main` и `dev`, PR в эти ветки, merge queue и вручную. Workflow находится в `.github/workflows/ci.yml`.

Параллельно выполняются три проверки:

- Go: форматирование, vet, генерация API, сборка, unit и PostgreSQL/E2E с race detector, нагрузочный сценарий и обе группы мутаций.
- Runtime: контейнер, миграции, readiness, SIGTERM и коллекция Postman.
- Simulator: HTTP-тесты эмулятора, пять сквозных сценариев и строгая сборка документации.

Итоговый статус `CI` успешен только после всех трёх проверок. Ошибка, отмена или пропуск любой из них блокирует успех. Логи и отчёты мутаций доступны в артефактах запуска семь дней. Настоящие токены MAX и другие секреты для проверок не нужны.

## Что проверяется

| Сценарий | Проверяемое свойство |
| --- | --- |
| Конкурентные запросы | Один код у одного получателя, один шанс за день |
| Полночь и ожидание блокировки | Событие не переключается на новый день или партнёра, сроки проверяются после ожидания |
| Сбой транзакции и повтор | Нет частичных назначений, заявок, призов или ответов |
| Повтор старой кнопки | Ввод имени и согласие для другого приза сохраняются |
| Десять дней действий | Веса финала соответствуют накопленным шансам |
| Получение приза и просрочка | Согласие обязательно; имя проверяется после блокировок; просроченное уведомление не отправляется при восстановлении очереди |
| Сообщения без текста | `text: null`, отсутствующая подпись и `body: null` получают ACK без изменения шансов, имени или очередей; текстовые подписи работают |
| Удалённое сообщение кнопки | Callback с `message: null` и без `message`, включая повторы и согласие на приз, получает HTTP `200` и `ignored: true`; очереди, данные и вызовы MAX не меняются |
| HTTP E2E | Webhook, worker, PostgreSQL, MAX-клиент, подтверждение розыгрыша, имя, согласие и резерв |
| Ошибки MAX | Retry-After сохраняется; восстановление доставки не продлевает срок приза |
| Лимиты MAX | Все методы делят 30 запросов/с; сообщения и ответы на кнопки дополнительно соблюдают два запроса/с на диалог; отменённый запрос не отправляется |
| Секрет webhook | Допустимы 16-256 символов ASCII: буквы, цифры, `_` и `-` |
| Календарный день | Два периода одной локальной даты и переход через полночь отклоняются; дни DST длиной 23/25 часов допустимы |
| Нагрузка исходящей очереди | 1000 разных получателей, отсутствие потерь и дублей; порядок внутри диалога и независимость занятых диалогов |

E2E использует локальный HTTP-сервер MAX и тестовые часы. Это проверка всего приложения без настоящего токена MAX. SQL-гонки проверяются разными соединениями PostgreSQL и управляемыми блокировками.

## Полный прогон

Запустите отдельную тестовую базу и передайте её адрес:

```sh
docker compose --profile test up --wait postgres-test
TEST_DATABASE_URL='postgres://promo_test:localtest-db-password@127.0.0.1:5433/promo_test?sslmode=disable' \
  make verify-local
```

Команда проверяет форматирование, vet, генерацию API, тесты mutation runner, все интеграционные тесты с race detector и обе группы мутаций. Отсутствие `TEST_DATABASE_URL` считается ошибкой.

Мутации временно возвращают 20 доменных и 8 межслойных ошибок через Go overlay. До изменения назначенный тест должен пройти, после изменения должен упасть. Ошибка сборки, пропуск и тайм-аут не засчитываются. Исходники не меняются; отчёты: `reports/mutations.json` и `reports/integration-mutations.json`. Отдельный запуск: `make mutate` и `make mutate-integration`.

Нагрузочный сценарий использует PostgreSQL, настоящий MAX-клиент и локальный HTTP-сервер платформы. Он выводит время доставки 1000 сообщений и скорость обработки. Общий лимит 30 запросов/с включён; только ожидание лимита занимает около 34 секунд. Отдельный запуск с заданным `TEST_DATABASE_URL`:

```sh
mkdir -p reports
go test -tags=integration -race -count=1 -v \
  -run '^TestOutboxDeliversThousandIndependentRecipients$' ./internal/app \
  > reports/outbox-load.log 2>&1
```

Лог сохраняется в `reports/outbox-load.log`. Результат описывает этот изолированный стенд; время ответа внешней платформы в него не входит. Каталог `reports/` исключён из Git.

`make coverage` показывает фактическое покрытие. 100% statements относится только к `internal/domain`. Мутации ограничены выбранными ошибками.

## Проверка контейнера

`make smoke` проверяет миграции, non-root, read-only, readiness, HTTP и SIGTERM. Нужны Docker, Python 3 и curl. Сценарий использует отдельные контейнеры и удаляет только свои данные. Для запуска самой Postman-коллекции дополнительно передайте `POSTMAN_CLI=/absolute/path/to/postman`.

## Стенд MAX-симулятора

```sh
make simulator-check
```

Команда поднимает отдельный стенд, запускает HTTP-тесты эмулятора и проходит пять сценариев через настоящий MAX-клиент сервиса, webhook и PostgreSQL: участие, пустой пул, дневной приз, финал и резерв. Проверяются повторная выдача кода, один дневной шанс, ошибка подписки, повтор события, проверка имени и обязательное согласие.

Проверки стенда включают блокировку служебных и URL-кодированных адресов, PNG во вложении и его отображение в чате. Healthcheck проверяет HTTPS-баннер на внутреннем порту 4011 с именем `simulator` и явным CA.

Стенд остаётся доступен для ручной проверки на [127.0.0.1:4010](http://127.0.0.1:4010/). Тест создаёт свои кампании. Для полного лога запуска: `make simulator-check > reports/simulator.log 2>&1`; сначала создайте каталог `reports`. Нужны Docker и Python 3. Остановка: `make simulator-down`.
