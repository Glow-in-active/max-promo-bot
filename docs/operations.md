# Подключение MAX

Для подключения бота нужны токен, права администратора в партнёрских каналах, внешний HTTPS webhook и доступный по HTTPS баннер PNG/JPEG. Создание бота описано в [документации MAX](https://dev.max.ru/docs/chatbots/bots-create/create).

## Симулятор

`make simulator` собирает отдельный стенд и открывает HTTP-порт `127.0.0.1:4010`. Для другого порта задайте `SIMULATOR_PORT`, например `SIMULATOR_PORT=4020 make simulator`. Обычный demo на порту 8080 работает независимо.

В основе лежит [MAX-эмулятор](https://github.com/620x/telegram-max-bridge/tree/2b4b2df7f16d2015077f29c23c7515894d2bf01f/max-emulator) с закреплённой версией исходников. Обёртка добавляет проверку подписки, браузерный чат и пересылку событий в сервис. Кнопки и сообщения проходят через MAX HTTP API, webhook, inbox/outbox и PostgreSQL.

Режим `simulator` использует MAX-клиент с локальным HTTP-адресом. Тестовые кампании создаются через защищённый API. Кампания закрепляется за пользователем на стороне стенда; браузер не задаёт адрес webhook и служебные токены. Подпиской управляет эмулятор, внутренний demo override отключён.

Баннер доступен внутри сети Compose по `https://simulator:4011/assets/banner.png`; порт 4011 на хост не публикуется. Сертификат содержит имя `simulator`, healthcheck проверяет HTTPS с явным CA. Браузерный чат загружает тот же PNG через свой HTTP-адрес. Служебные адреса эмулятора, включая `/subscriptions`, и пути с URL-кодированием возвращают `404`.

Контейнеры и база принадлежат отдельному Compose-проекту `promo-simulator`. `make simulator-down` сохраняет базу. Перезапуск эмулятора сбрасывает историю его чатов; создайте новый сценарий в браузере.

## Настройки

Скопируйте `.env.example` в `.env` и заполните:

| Переменная | Значение |
| --- | --- |
| `MODE` | `production` |
| `ADMIN_TOKEN` | Приватный токен, минимум 24 символа |
| `MAX_TOKEN` | Токен бота |
| `MAX_WEBHOOK_SECRET` | 16-256 символов: латинские буквы ASCII, цифры, `_` и `-` |
| `CAMPAIGN_ID` | ID импортируемой акции |
| `MAX_BANNER_URL` | HTTPS URL баннера |
| `MAX_CA_FILE` | При необходимости путь к смонтированному PEM дополнительного CA |

Локальные токены в production отклоняются, demo-маршруты отключены.

При нативном запуске `HTTP_ADDR` задаёт адрес HTTP-сервера, по умолчанию `:8080`. Команда `promo healthcheck` проверяет `/readyz` на том же адресе без подключения к БД или MAX; дополнительные аргументы не принимает. В Compose сервис слушает порт `8080`, а `HTTP_PORT` задаёт порт на хосте.

## Подключение PostgreSQL

В `.env.example` параметры базы собраны в отдельном блоке:

| Переменная | Назначение и значение по умолчанию |
| --- | --- |
| `POSTGRES_HOST` | В Compose `postgres`; при нативном запуске без этой переменной `localhost` |
| `POSTGRES_PORT` | Порт подключения, `5432` |
| `POSTGRES_DB` | Имя базы, `promo` |
| `POSTGRES_USER` | Пользователь, `promo` |
| `POSTGRES_PASSWORD` | Пароль подключения; в локальном Compose `localdemo-db-password` |
| `POSTGRES_SSLMODE` | Режим TLS, по умолчанию `disable` для локального стенда |

Приложение и команды `migrate`/`setup` используют эти значения. Для внешней базы укажите её адрес, порт, пользователя и нужный SSL mode. Пароль кодируется при сборке URL; специальные символы и IPv6 поддерживаются.

Непустой `DATABASE_URL` полностью переопределяет компоненты, включая порт и SSL mode. Это сохраняет нативные сценарии с готовой строкой подключения. При запуске на хосте задайте `POSTGRES_HOST=127.0.0.1` либо оставьте переменную незаданной.

Параметры пула задаются в `DATABASE_URL` через `pool_max_conns` и другие настройки pgx; сервис сохраняет их значения.

`POSTGRES_PORT` задаёт и порт сервера PostgreSQL внутри Compose, и порт подключения приложения. По умолчанию это `5432`; основной порт базы наружу не публикуется. Значения пользователя, базы и пароля применяются при создании нового тома; существующие роли и базы изменяются отдельно. Текущий том и его данные сохраняются.

## Импорт и запуск

Скопируйте `config/campaign.example.json` в `config/campaign.json`. Укажите реальные даты, каналы, ссылки, коды, призы и сроки. ID должен совпадать с `CAMPAIGN_ID`.

```sh
docker compose build migrate
docker compose up --wait postgres
docker compose run --rm migrate
docker compose run --rm \
  --volume "$PWD/config/campaign.json:/config/campaign.json:ro" \
  migrate setup /config/campaign.json
docker compose up --build --wait app
```

Импорт проверяется и сохраняется одной транзакцией. Существующий ID не перезаписывается. Локальный конфиг исключён из Git и Docker build context.

Файл содержит один JSON-документ размером до 2 MiB. Неизвестные поля, лишний документ, пустые секреты и некорректные ссылки отклоняются до запуска. На миграции и импорт отводится одна минута.

Готовые сообщения должны укладываться в [лимит MAX в 4000 символов](https://dev.max.ru/docs-api/methods/POST/messages). Импорт проверяет правила, промокоды с инструкциями, приглашения к участию, уведомления о призах и сводку всех десяти дней с текстом регистрации. Длина считается в кодовых точках Unicode, текст не обрезается.

У кнопок отдельные [лимиты](https://github.com/max-messenger-bot/max-bot-api-schemas/blob/main/schema_2026_07_01.json): подпись от 1 до 128 символов, callback payload до 1024, ссылка до 2048. Ссылка партнёра проверяется при импорте. Кнопка подписки называется «Подписаться на канал», имя партнёра указано в сообщении.

Сообщение из существующей базы с недопустимой длиной текста или полей кнопок отклоняется до HTTP-запроса. Задание получает `failed`, срок получения приза не начинается.

Настройте подписку MAX на `bot_started`, `message_created`, `message_callback` и внешний endpoint `/webhooks/max` с тем же секретом. TLS и публичный адрес настраиваются в инфраструктуре размещения: Compose публикует сервис только локально.

## Логи

`LOG_LEVEL` принимает `debug`, `info`, `warn` или `error`, по умолчанию `info`. Сервис пишет структурированный JSON на английском.

| Уровень | События |
| --- | --- |
| `debug` | HTTP-запросы, получение и завершение заданий |
| `info` | Запуск, остановка, импорт, розыгрыши и подтверждение результатов |
| `warn` | Отклонённые запросы и запланированные повторы |
| `error` | Ошибки сервиса и окончательно не доставленные сообщения |

Тела запросов, токены, промокоды и имена не логируются. Для связи записей используются стабильные хеши ID. Просмотр: `make logs`; включение подробных логов: `LOG_LEVEL=debug make up`.

## Восстановление доставки

Посмотрите `delivery_state` и `delivery_error` через `GET /api/admin/campaigns/{campaign}/draws/{draw}/offers`.

- При `delivery uncertain` проверьте, дошло ли сообщение. Подтвердите доставку через `POST /api/admin/offers/{offer}/delivered` или повторите через `POST /api/admin/offers/{offer}/retry`.
- При отказе или исчерпании попыток исправьте причину и выполните `retry`. Операции требуют административный токен.

До подтверждения доставки срок получения приза не начинается и резерв не вызывается. Нажатие кнопки владельцем тоже подтверждает доставку. Повторная отправка не продлевает начатый срок.

После истечения срока бот не принимает имя для этого приза и не отправляет повторное уведомление о выигрыше. Для уже полученного приза уведомление тоже пропускается. Ожидание лимита MAX входит в оставшееся время отправки.

Все вызовы MAX делят лимит 30 запросов в секунду. Отправка сообщений и ответы на кнопки дополнительно ограничены двумя запросами в секунду на диалог. Для 1000 получателей закладывайте около 34 секунд только на лимит, без учёта задержек и других API-вызовов.

`/healthz` проверяет HTTP-процесс, `/readyz` проверяет подключение к PostgreSQL. `make down` сохраняет данные; `docker compose down --volumes` удаляет их.
