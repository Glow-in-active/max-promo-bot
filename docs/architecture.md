# Устройство сервиса

Один Go-процесс принимает HTTP, обрабатывает события и запускает фоновые задачи. Данные и очереди находятся в PostgreSQL.

## Код

| Каталог | Назначение |
| --- | --- |
| `cmd/promo` | Команды, сборка зависимостей и остановка |
| `internal/config` | Настройки окружения и их проверка |
| `internal/transport/httpapi` | HTTP, события MAX, авторизация и проверка контракта |
| `internal/app` | Сценарии, транзакции и фоновые обработчики |
| `internal/domain` | Правила, состояния и выбор победителей |
| `internal/storage/postgres` | SQL, блокировки, миграции, inbox и outbox |
| `internal/platform` | Адаптеры MAX и demo |

Domain не зависит от HTTP и PostgreSQL. Application использует интерфейсы хранилища, платформы, часов и случайности. Источник HTTP-контракта: `api/openapi.yaml`; типы и маршруты генерирует `oapi-codegen`.

## Целостность

Правила проверяются в Go под блокировками. Ограничения PostgreSQL дополнительно защищают уникальность и связи. Порядок блокировок: акция, розыгрыш, пользователь, пул, призовое место.

| Ситуация | Защита |
| --- | --- |
| Параллельная выдача кода | Блокировки пользователя и пула, сохранённое назначение |
| Код и регистрация в один день | Общая дневная активность и правило `GrantChance` |
| Регистрация одновременно с розыгрышем | Блокировка розыгрыша до сохранения состава |
| Активность одновременно с финалом | Эксклюзивная блокировка акции |
| Получение приза одновременно с просрочкой | Блокировка одного призового места и повторное чтение состояния |
| Отправка одновременно с ручным повтором | Общая блокировка получателя при выдаче задания; один активный lease на диалог |

Подписка проверяется вне транзакции. После ожидания блокировок заново проверяются сроки и состояние. Дневное действие привязано к исходному времени события MAX.

Бизнес-изменения, завершение inbox и ответ в outbox коммитятся вместе. Незавершённое задание освобождается через 30 секунд. Worker учитывает Retry-After; неопределённая доставка приза требует [решения оператора](operations.md). Внешнее сообщение после сбоя может прийти повторно.

Outbox обрабатывают восемь workers. Пока есть сообщения, они продолжают работу без паузы опроса. В одном диалоге сохраняется порядок сообщений, занятый диалог не задерживает остальных. Общий [лимит MAX-клиента](https://dev.max.ru/docs-api/use-cases/event-notifications) составляет 30 HTTP-запросов в секунду, включая подписки, сообщения и ответы на кнопки. Дополнительно действуют два запроса в секунду на диалог отдельно для [сообщений](https://dev.max.ru/docs-api/methods/POST/messages) и [ответов на кнопки](https://dev.max.ru/docs-api/methods/POST/answers).

HTTP-запрос ограничен десятью секундами, отдельное фоновое задание пятнадцатью. Планировщик продолжает обработку остальных заданий после ошибки одного. Отменённая операция не подтверждает доставку, её lease восстанавливается штатно.

При вводе имени состояние приза и срок проверяются после блокировки места. Устаревшее действие очищает только ввод для своего приза. Уведомления по просроченным и уже полученным призам пропускаются; ожидание лимитера входит в срок отправки.

## Принятые правила акции

[Исходное задание](https://docs.google.com/forms/d/e/1FAIpQLSdpM_xCLX08y2BNWAzvAqYjrG78O249iSpuTuSCznZ9BU5sig/viewform).

- Начало дня включено, конец исключён. Каждый период принадлежит одной календарной дате в часовом поясе акции; два периода одной даты отклоняются при импорте. Полночь следующего дня допустима как исключённая граница, переходы DST учитываются.
- Подписка проверяется при регистрации, перед розыгрышем повторно не запрашивается. Ошибка MAX не считается отсутствием подписки.
- Код и заявка дают один общий шанс за день. Пустой пул не мешает регистрации. При повторном появлении партнёра в другой день можно участвовать снова.
- Финал выбирает пять разных людей с весами по активным дням, каждому по два билета. Выбранный человек исключается из следующих мест. Дневной выигрыш не лишает права на финал.
- Состав, веса, победители и порядок резерва сохраняются. Повторный запуск возвращает тот же результат. Если кандидатов меньше мест, выбираются доступные; при исчерпании резерва нового выбора нет.
- На розыгрыш задаются число победителей, резерв и одинаковый набор приза для каждого победителя. Уведомления создаются после подтверждения администратора.
- Остатки группируются по каналу партнёра с детализацией дней. CSV читает участников, исходный выбор и текущие предложения из одного snapshot.

Сообщения дедуплицируются по MID, callback по времени, пользователю, callback ID и payload. Повторная доставка не создаёт новый запрос. Общий outbox позволяет отправлять уведомления; отдельного API массовых рассылок нет.

Фото без подписи, пустой текст и пересылки с `body: null` получают HTTP `200` и `ignored: true`. Так же обрабатывается callback с `message: null` или без исходного сообщения: контекст диалога неизвестен, действие не выполняется. Эти события не попадают в inbox и не меняют шансы или ввод данных для приза. Непустая подпись обрабатывается как текст.

Runtime работает на `scratch` от UID/GID 65532 с read-only файловой системой. Миграции запускаются перед приложением, SIGTERM завершает HTTP и workers.

Для ручной проверки есть отдельный Compose-стенд с браузерным чатом и MAX-эмулятором. Режим `simulator` использует тот же MAX-клиент, что production, и свою PostgreSQL. Локальные сценарии создают данные для участия, розыгрышей, финала и резерва. Чат показывает PNG из вложения; служебные маршруты эмулятора и пути с URL-кодированием возвращают `404`. [Запуск](operations.md).
